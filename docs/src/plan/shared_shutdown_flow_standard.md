# 公共收尾失能流程标准方案

## 目标

把当前仅存在于 [`scripts/move_debug.py`](/home/xinger/MyWork/piper_control_demo/scripts/move_debug.py) 第 110 行到 139 行附近的“结束后是否失能”流程，抽取到 [`src/piper_control_demo`](/home/xinger/MyWork/piper_control_demo/src/piper_control_demo) 作为公共模块。

这次的目标不是只为了让 `move_debug.py` 更短，而是把它提升为可复用的项目标准：

- 以后凡是会真实驱动机械臂、并在任务结束后需要人工决定是否回安全位和失能的脚本
- 都应默认考虑复用这套公共收尾流程

并且这条标准也要写进文档。

## 当前这段代码实际承担的职责

`scripts/move_debug.py` 当前第 110 到 139 行虽然表面上看是“结束后是否失能”，但实际上承担了 4 类职责：

1. 根据上下文生成不同提示语
   - 正常完成
   - 急停中断
2. 询问操作者是否进入失能流程
3. 如果需要失能：
   - 先回安全位
   - 再失能夹爪
   - 再失能机械臂
4. 如果安全位未达到：
   - 取消失能
   - 打印当前状态

所以它本质上不是一段简单 `input()`，而是一段完整的“收尾/退场控制流程”。

## 为什么值得抽公共模块

这段逻辑在真实机械臂项目里很容易重复出现。

比如后续任何脚本只要满足这些条件，就大概率需要类似流程：

- 前面已经真实运动过机械臂
- 结束时不想直接自动掉使能
- 希望由操作者决定是否回安全位
- 回安全位后希望统一处理夹爪和机械臂失能

如果每个脚本各写一份，会出现几个问题：

- 提示语不一致
- 安全位逻辑可能漂移
- 失能顺序可能不一致
- 某些脚本可能漏掉夹爪失能

因此，把这套逻辑上升为公共能力是合理的。

## 功能方案判断

这个需求和之前已经抽取的“公共软件层急停”是同一类问题：

- 都属于真实机械臂控制脚本的公共安全能力
- 都应该从业务脚本里抽出去
- 都应形成文档标准

所以这次抽取很自然，而且方向正确。

- 脚本导入时也更集中

## 应该抽出什么样的公共能力

这次建议抽出一个“收尾失能流程函数”，而不是只抽一段提示语。

例如可以设计为：

- `confirm_and_shutdown(...)`

它的职责应包括：

1. 根据任务状态生成提示语
2. 读取操作者确认
3. 如果不确认，则直接返回
4. 如果确认，则进入回安全位流程
5. 回安全位成功后，统一处理夹爪失能和机械臂失能
6. 回安全位失败时，打印说明并放弃失能

## 建议接口形态

为了后续脚本复用，建议参数尽量通用一些。

例如：

```python
confirm_and_shutdown(
    robot=robot,
    controller_factory=...,
    safe_position=[...],
    safe_speed=...,
    threshold=...,
    timeout=...,
    emergency_stop_triggered=...,
)
```

关键点在于：

- 它不能把 `move_debug.py` 里所有变量写死
- 但也不应复杂到让每个脚本都难用

## 为什么要传 controller_factory

当前 `move_debug.py` 的安全位逻辑是：

```python
with piper_control.BuiltinJointPositionController(robot, rest_position=None) as controller:
    ...
```

如果公共函数内部也要做“回安全位”，它就需要创建控制器。

这里有两个方向：

### 方案 A：公共函数内部直接写死 BuiltinJointPositionController

优点：

- 最简单

缺点：

- 绑定太死
- 以后如果有别的控制器，不好复用

### 方案 B：通过参数传入控制器构造方式

优点：

- 更灵活
- 以后同一套收尾逻辑可以服务更多脚本

缺点：

- 接口稍复杂一点

我更倾向方案 B，但如果你想优先最小改动，这次也可以先做 A。

## 当前 move_debug.py 后续应如何改造

一旦公共函数存在，`move_debug.py` 的尾部应该尽量只剩：

1. 计算/记录：
   - `emergency_stop_triggered`
   - `safe_position`
2. 调用公共收尾函数
3. 接收返回结果

也就是说，把现在第 110 到 139 行里这几类逻辑搬出去：

- prompt 生成
- yes/no 判断
- 安全位移动
- 夹爪失能
- 机械臂失能
- 失败提示

`move_debug.py` 只保留本脚本特有的目标位和过程控制。

## 这套公共流程的建议边界

这套“公共收尾失能流程”建议默认处理下面这些事：

### 1. 提示语分支

至少区分：

- 正常结束
- 急停中断

因为这会直接影响操作者的判断。

### 2. 回安全位

建议公共函数内部支持：

- 指定 `safe_position`
- 指定 `speed`
- 指定 `threshold`
- 指定 `timeout`

### 3. 失能顺序

建议统一成：

1. 先 `robot.disable_gripper()`
2. 再 `piper_init.disable_arm(robot)`

这样项目内所有脚本都保持一致。

### 4. 返回值

建议返回一个结构明确的结果，例如：

- 用户是否请求失能
- 是否到达安全位
- 是否最终完成失能

这样业务脚本后续可以决定是否再补日志或状态显示。

## 和公共软件层急停的关系

这次抽取后的整体结构会更清晰：

- 运动中：
  - 由公共软件层急停能力负责
- 运动结束后：
  - 由公共收尾失能流程负责

两者都是“真实机械臂控制脚本默认应复用的公共安全能力”。

这很重要，因为以后文档可以直接形成一套标准说法：

- 进入运动前要明确安全参数
- 运动中默认接入公共软件层急停
- 结束后默认接入公共收尾失能流程

## 文档中应写成什么标准

建议在文档中写成明确约定，而不是只写“move_debug.py 目前这么做”。

推荐表述：

- 对真实机械臂控制脚本，若存在人工确认后可选回安全位和失能的流程，应优先复用公共收尾失能模块，保持提示语、回安全位和失能顺序一致。

以及：

- 软件层急停和收尾失能流程应共同视为项目内默认的安全复用能力。
